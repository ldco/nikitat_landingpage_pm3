# PM3 Shop — расширение фреймворка для «поточной» сборки интернет-магазинов (v1)

**Date:** 2026-09-03
**Return:** планирование shop-модуля приостановлено — вернуться к этому плану после завершения текущего сайта (this site).
**Status:** Approved (согласовано на сессии планирования; финализировано 2026-09-03)

---

## 1. Контекст и цель

PM3 — конфигурируемый движок сайтов (SvelteKit): `ENTITIES.website/app`,
`FEATURES.onepager`, секции с `renderMode: section|page`, реестры с override
на project-слое. Жёстких допущений о форме сайта фреймворк не делает.

**Гипотеза:** появится поток заказов на создание интернет-магазинов (B2C, РФ).
Первый клиент пока неизвестен — вертикаль, платёжный и логистический провайдеры
выбираются вместе с ним. Стратегия: первый клиент должен остаться в восторге
(сарафан) → продукт делается сразу производственного уровня.

**Цель:** сделать PM3 технически готовым собирать магазины поточной линией:
(а) shop-возможность в ядре фреймворка (этот план), (б) генератор project-слоя
из «рецепта» (recipe), (в) демо-шаблон первого клиента.

---

## 2. Принципы

1. **Фреймворк не предполагает форму сайта.** Магазин — композиция существующего
   движка (`ENTITIES.shop` + конфиг + реестры), а не «особый режим».
2. **Отдаём шов, а не монолит.** Ядро v1 = ограниченная модель товара +
   типизированные характеристики + декларативные определения атрибутов
   (project-слой). Runtime EAV и per-category attribute-set движки — плагины, не ядро.
3. **Три поверхности продукта:** витрина (покупатель) / админка владельца
   (white-label) / консоль PM (обслуживание). Границы поверхностей = продукт:
   владелец управляет контентом и заказами, PM — сервером, ключами и кодом.
4. **Схема — в конфиге (код project-слоя), контент — в БД.** Определения
   атрибутов/структура — builder; значения — владелец, ежедневно.
5. **Заказ — корневой объект.** Покупатель-гость первичен, регистрация не нужна;
   личность покупателя — проекция заказа, а не предусловие.
6. **Провайдеры — только интерфейсы в ядре.** Оплата/доставка/маркетплейсы
   подключаются конфигом под конкретного клиента.
7. **Правила РФ встроены в поток:** 152-ФЗ, ЗоЗПП (ст. 26.1, ПП №2463),
   54-ФЗ чеки — не «потом», а часть дизайна v1.

## 4. Конфигурация (добавления в конфиг-слой)

- `ENTITIES: { website, app, shop }` — новое измерение; shop по умолчанию `false`.
- Новые `FEATURES`: `catalog`, `cart`, `checkout`, `orderTracking`, `catalogSearch`
  (FTS5), `buyerAccounts` (off), shop-хедер (search/корзина/меню категорий).
- `MODULES.shop` — enabled + config.
- `SHOP_CONFIG` (project layer): `currency: 'RUB'`, деньги — **integer minor units**;
  `stockMode: 'reserve-on-pay'`; `nav.categoriesDepth`; реквизиты продавца (L3);
  настройки уведомлений; включённые провайдеры оплаты/доставки.
- `catalog-attributes.ts` (project layer): `PRODUCT_ATTRIBUTES` — единый источник
  определений (`key`, `label`, `type: string|number|boolean|enum`, `ui`,
  `options`, `unit`, `filterable`, `variantDimension`, `categoryIds?`),
  → генерируемая Zod-схема на все write-границы (паттерн `portfolio-metadata.ts`).
- Роли: роль `shopkeeper` в существующей ролевой модели; white-label флаг в конфиге админки.

## 5. Модель данных (конвенции ADR-001: base + per-locale translations)

1. **Каталог**
   - `shop_categories` (parent-FK дерево) + `shop_category_translations`
   - `shop_products` + `shop_product_translations` (name, description, seo_*)
   - `shop_variants` (sku, цена опц., compare_at опц., quantity, reserved, media, active)
   - `shop_variant_modifiers` (variant_id, attribute_key, value) — single-language (D5)
   - `shop_product_attribute_values` (typed columns value_text/number/boolean;
     `(product_id, attribute_key)` unique) — фильтры/спецификации
   - `shop_product_media` (kind: cover|gallery, sort)
2. **Заказ**
   - `shop_customers` — покупатель (отдельно от admin-пользователей)
   - `shop_carts` + `shop_cart_items` — серверная корзина, cookie-сессия гостя
   - `shop_orders` + `shop_order_items` — **снапшоты цены и данных покупателя**
   - `shop_payments`, `shop_deliveries` — ссылки на транзакции провайдеров
   - на заказе: версия/дата/IP согласия на обработку ПДн (L2)

**Ценовой резолвер (единственная точка истины):**
`effectivePrice(variant) = variant.price_minor ?? product.price_minor`.
При активных вариантах цена товара не продаётся: карточка каталога = мин.
эффективных цен («от N ₽»). Остатки — всегда на варианте.

**Машина состояний заказа (ядро):**
`draft → pending_payment → paid → assembling → shipped → delivered`,
плюс `cancelled / refunded`. Каждый переход аудируется; вебхуки идемпотентны.
Таймлайн заказа общий для админки владельца и публичной страницы
`/order/[number]` (убивает звонки «где мой заказ»).

## 6. Storefront: архетипы и композиция

- `PAGE_REGISTRY` — зеркало `SECTION_REGISTRY`: framework-страницы + override
  project-слоя (project wins). Тонкие роуты-обёртки (как `[section]`),
  каждый архетип 404/redirect, если модуль выключен (проверка в load).
- **Роуты v1 (D9):** `/catalog`, `/catalog/[category]`, `/product/[slug]`, `/cart`,
  `/checkout`, `/order/[number]`, `/search`.
- Typed load-контракты на архетип (Zod), сервисы в `$lib/server/services/*`.
- Главная магазина = существующий движок секций + новый `SectionProducts` (D10)
  (featured/latest), включается через `HOMEPAGE_SECTIONS`.
- Shop-aware `TheHeader`: поиск, бейдж корзины, меню категорий из БД
  (глубина из конфига) — через данные `+layout.server.ts`, gated по модулю.
- Серверная корзина: signed cookie гостя → `shop_carts`; CSRF на мутациях;
  пересчёт цен/остатков на checkout (никогда не доверять клиенту).
- SEO: schema.org Product/Offer/BreadcrumbList JSON-LD, canonical,
  **sitemap.xml** (товары + категории) — в ядре.

## 7. Админка владельца (shopkeeper)

- Роль видит **только группу Shop**; системное (users/roles/translations/security/
  ключи/инфраструктура) недоступно. White-label chrome (логотип/имя клиента,
  скрыты ссылки PM/версия). RU.
- **IA (D12/D14):** Dashboard / Заказы / Товары (каталог, категории,
  характеристики-значения, CSV импорт/экспорт) / Клиенты (+DSAR) /
  Контент (страницы/блог, если включено) / Настройки магазина.
- **Dashboard:** KPI (сегодня: заказы, выручка = paid − refunds, средний чек),
  очередь заказов «требуют действия», низкие остатки, быстрые действия,
  новый заказ → Telegram.
- **Товары:** форма генерируется из `PRODUCT_ATTRIBUTES` (виджеты по типу);
  матричный редактор вариантов (цена опц. = наследование); галерея drag-drop;
  копирование товара; массовые операции (публикация/скрытие/перенос/±% цены);
  CSV импорт прайса.
- **Заказы:** фильтры по статусу; карточка с таймлайном, оплатой (возврат:
  частичный, причина, подтверждение — D13), доставкой (трек/статус), печать накладной.
- **Клиенты:** поиск, заказы клиента; **DSAR-инструменты**: экспорт данных и
  удаление покупателя с каскадом персональных данных (152-ФЗ), с аудитом.
- **Настройки магазина:** реквизиты (L3), способы доставки/оплаты (без ключей!),
  уведомления, юридические документы.
- Новые примитивы PM3 (дополнить canonical-список и валидатор check #6):
  `StatCard`, `StatusBadge`, `OrderTimeline`, `VariantMatrixEditor`,
  `BulkToolbar`, `DataTableFilters`.

## 8. Адаптеры — интерфейсы в ядре, реализации под клиента

```ts
// src/lib/server/commerce/providers/*
interface PaymentProvider { createPayment(order): PaymentIntent;
                           handleWebhook(req): Result; refund(payment): Result }
interface DeliveryProvider { getRates(cart, address); createShipment(order);
                             getTracking(id) }
interface CatalogImportSource { pull() }   // маркетплейсы — вне v1
```
- Реестр по id провайдера; выбор конфигом (`SHOP_CONFIG.payments.provider`).
- v1: **sandbox/test-платёжный провайдер** + идемпотентный вебхук-скелет;
  54-ФЗ чек — через платёжного провайдера. Доставка v1: ручные методы + самовывоз.
- Модуль ядра `src/lib/server/commerce/*`: машина состояний, cart, checkout,
  провайдеры, уведомления (reuse `email.ts` / `telegram.ts`).

## 9. Юридический пакет (framework) — решения L1–L5

- **Производство документов (L1):** RU-шаблоны в ядре: оферта (розничная
  купля-продажа, ст. 26.1 ЗоЗПП, ПП №2463) + политика ПДн покупателей.
  Заполняются реквизитами при создании магазина → кладутся в legal docs как
  редактируемые документы (существующая админка legal). Перед запуском —
  compliance-чек-лист PM (L5). Финальная юр. проверка — мерчант.
- **Consent (L2):** кнопка = акцепт оферты; чекбокс ПДн (не предотмечен);
  маркетинга нет; на заказе хранятся версия/дата/IP согласия.
- **Реквизиты (L3):** JSON-настройка + Zod; блок в футере + подстановка в
  оферту/контакты; обязательны перед запуском; валидация контрольной суммы.
- **Возврат 7/10 дней (L4):** полный текст в оферте + ссылка на checkout +
  памятка в письме-подтверждении.
- **Процесс запуска (L5):** чек-лист-шаблон `docs/operations/` (РКН-уведомление,
  эквайринг/54-ФЗ, СБП-пороги, договоры доставки, юр. проверка оферты, сервер РФ).
  В коде — только гейт «реквизиты + legal-доки заполнены».
- Куки-consent до Метрики (существует). Локализация БД — на территории РФ.

## 10. Консоль PM (M6) — решения C1–C4

Продукт ежемесячного обслуживания. Реализуется после первого реального деплоя
(out-of-scope #14), спецификация зафиксирована здесь.

- **Расположение (C1):** ops-страницы PM-роли в каждом магазине (`/admin/ops/*`):
  health (существующий отчёт), версия ядра + версия схемы БД, бэкапы, деплой,
  последние ошибки; метрики не покидают магазин. Fleet-агрегатор (читает
  health-эндпоинты магазинов) — позже.
- **Бэкапы (C2):** планировщик в контейнере магазина: онлайн-бэкап SQLite
  (`VACUUM INTO`), ретеншен (≈14 ежедневных + месячные), РФ-хранилище;
  ops-страница: время/возраст/размер + «сделать сейчас»; restore-runbook +
  ежемесячный тест восстановления.
- **Алерты (C3):** Telegram PM: health fail, протухший бэкап, всплеск 5xx,
  внешний heartbeat.
- **Версии/откат (C4):** pinned image tag версии ядра; миграции при деплое;
  rollback = предыдущий тег + восстановление БД из бэкапа; история деплоев в
  audit; индикатор «доступно обновление».
- **Доступ:** ops-действия только PM-роль (существующие auth + 2FA + audit);
  ключи/секреты — только в окружении PM, не в админке владельца.

| **M2** | Коммерческое ядро: гостевая корзина/заказ (cookie-сессия, CSRF), машина состояний, `PaymentProvider` + sandbox + идемпотентный webhook (54-ФЗ шов), `DeliveryProvider` (ручные + самовывоз), checkout (одностраничный), юрпакет в потоке (оферта-шаблон, чекбокс ПДн, реквизиты+футер+гейт, возвраты-текст), `/order/[number]`, письма (владелец+покупатель, памятка о возврате), резерв остатков | D2, D8, D12; L1–L4 | M1 | e2e «каталог → корзина → checkout → sandbox-оплата → заказ в админке»; согласие/оферта хранятся на заказе; гейт реквизитов работает |
| **M3** | Админка владельца: роль shopkeeper, white-label, dashboard, заказы (статусы, возврат с причиной, накладная, таймлайн), товары (матрица вариантов, bulk, CSV, копирование), клиенты + DSAR (экспорт/удаление), настройки магазина; новые примитивы + валидатор | D4, D13, D14 | M2 | shopkeeper не видит системное; white-label; мобильный UX; refunds только владелец; e2e по критическим потокам |
| **M4** | Юридическое завершение + готовность провайдеров: compliance-чек-лист `docs/operations/` (L5), финальные шаблоны доков, доки «как подключить ЮKassa/СДЭК», security/e2e-гейт по всему shop | L5 | M2 | чек-лист существует и прогоняется; добавление реального провайдера = только новый адаптер, интерфейс не меняется; валидатор покрывает shop |
| **M5** | Демо-магазин + заводская линия: recipe → генерация (вкл. `catalog-attributes` вертикали, legal-доки, реквизиты) → seed → валидатор → build → deploy; демо с наполнением и админкой владельца | C1 (границы ролей) | M3+M4 | из recipe.json за ограниченное число ручных шагов получается рабочий магазин с наполнением и админкой; smoke-e2e проходит |
| **M6** | Консоль PM: ops-страницы, бэкапы, алерты, версии/откат (§10) | C1–C4 | первый реальный деплой | алерты и бэкапы работают на живом магазине; restore-тест проведён |

**Порядок:** M0 → M1 → M2 → M3 → M4 → M5 (M6 после первого деплоя).
M3/M4 после M2 взаимозаменяемы по приоритету первого клиента.

## 12. Риски и открытые вопросы

- Вертикаль, платёжный/доставочный провайдер, мерчант — решаются с первым клиентом.
- Юридический статус: PM строит продукт, мерчант — владелец юрлица (ККТ,
  договор эквайринга, РКН). Продукт делает это конфигурируемым (L5).
- Hosting не выбран → предположение: per-shop контейнер (ansible + docker + traefik),
  БД и бэкапы на территории РФ.
- Объём M0–M5 значителен; порядок этапов сохраняется, приоритизация — по первому клиенту.
