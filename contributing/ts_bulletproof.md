# TypeScript Bulletproof — PM Framework Standard

The PM framework enforces a 5-layer TypeScript safety system. Every line of code must pass all layers.

---

## 1. Tsconfig Lockdown (Compiler)

```jsonc
{
  "strict": true,                   // Master switch: strictNullChecks, noImplicitAny, etc.
  "noUncheckedIndexedAccess": true,  // obj[key] returns T | undefined
  "noImplicitOverride": true,        // Must use override keyword
  "isolatedModules": true,           // Safe for transpile-only tools
  "verbatimModuleSyntax": true       // import type is enforced at emit
}
```

**Status:** All Nuxt-generated tsconfigs enforce `strict: true`.  
**File:** `.nuxt/tsconfig.json` (auto-generated by Nuxt 4)

---

## 2. Zod Runtime Validation (Boundary)

Every untrusted data source crossing into the application must pass through a Zod schema.

**Convention:**
```typescript
// server/utils/validation.ts — central validation module
export const contactSchema = z.object({
  name: z.string().min(2).max(100),
  email: z.string().email(),
  message: z.string().min(10)
})
```

**Coverage:**
- All API request bodies validated with Zod
- Environment variables validated in `server/utils/env.ts`
- Translation payloads validated in `server/utils/translationValidation.ts`
- 361+ Zod usages across the codebase

**Status:** Fully enforced at every API boundary.

## 3. Escape Hatch Ban (Lint)

The following TypeScript escape hatches are banned by ESLint at the `error` level:

| Rule | Level | Purpose |
|------|-------|---------|
| `@typescript-eslint/no-explicit-any` | `error` | Never use `any` type |
| `@typescript-eslint/ban-ts-comment` | `error` | Never use `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck` |
| `@typescript-eslint/no-non-null-assertion` | `warn` | Avoid `!` operator (use proper null checks) |

**Conventions for safe type assertions:**
```typescript
// NEVER
const data = response as any
const value: any = config

// ALWAYS
const data = response as unknown as SpecificType
let value: unknown = config

// NEVER
catch (e: any) { }

// ALWAYS
catch (e: unknown) {
  const err = e as { data?: { message?: string } }
}
```

**Status:** `error` for `any` and `@ts-*` comments (zero violations). `warn` for non-null assertions (52 existing in production code to be cleaned up).

## 4. Discriminated Unions (Architecture)

Use a single literal property to narrow object shapes at compile time.

**Convention:**
```typescript
type PortfolioItem =
  | { itemType: 'image'; mediaUrl: string; caption?: string }
  | { itemType: 'video'; mediaUrl: string; duration?: number }
  | { itemType: 'case_study'; title: string; content: string }
```

**Existing usage in PM:**
- `type: 'gallery' | 'case_study'` in portfolio entities
- `status: 'ok' | 'error' | 'warning'` in health checks
- `status: CheckStatus | HealthStatus | MonitoringStatus` in admin types

**Status:** Pattern exists but not formally required for new entities. Every entity with multiple shapes should use discriminated unions.

---

## 5. Exhaustiveness Checking (`never`)

Use the `never` type to force compile-time errors when a switch/case doesn't handle all variants.

**Convention:**
```typescript
function handleItem(item: PortfolioItem): string {
  switch (item.itemType) {
    case 'image':
      return `Image: ${item.caption}`
    case 'video':
      return `Video: ${item.duration}s`
    case 'case_study':
      return `Article: ${item.title}`
    default:
      const _exhaustive: never = item
      throw new Error(`Unhandled itemType: ${(item as PortfolioItem).itemType}`)
  }
}
```

**Status:** Enforced. 3 switch statements made exhaustive with `never`-typed default branches (`image-assets.ts`, `workflow-paths.ts` x2). All existing discriminated unions are exhaustively handled. New discriminated unions must follow this pattern.

## Quick Reference: Anti-Patterns

```typescript
// ANTI-PATTERN — escapes the type system
const data: any = JSON.parse(input)
const name = user!.name
// @ts-ignore
catch (e: any) { console.log(e.message) }
type Status = 'ok' | 'error'  // no discriminator, no exhaustiveness

// CORRECT — works with the type system
const result = userSchema.safeParse(input)
const name = user?.name ?? 'Unknown'
catch (e: unknown) {
  const err = e as { message?: string }
  console.log(err.message)
}
type Status =
  | { kind: 'ok'; data: ResponseData }
  | { kind: 'error'; message: string }
// + exhaustiveness check in consumers
```
